# Teacher customization, approval, monthly renewal, email and student/admin UX

Date: 2026-10-10. Status: expanded concrete design for user review before implementation.

## Intent and agreed scope

Teachers can create any subject and their own years or student categories, then use them in the existing guided group creation flow and profile specializations. The user confirmed these choices belong only to their creator; students see the labels on published groups. Preserve English/Arabic, mobile usability, saved drafts, existing scheduling behavior and authorization. Sol designs/reviews; the previously approved GPT-6 Luna performs scoped implementation tasks.

Examples: a teacher creates Robotics and Year 3, or Conversational English and Adults / Beginners. No school or university hierarchy is required for their custom categories. Existing platform subjects and academic contexts remain available.

## Recommended experience

- Add a bilingual Subjects & categories page to teacher navigation. Separate sections manage subjects and years/student categories.
- Allow create, rename, archive and restore. Archiving hides choices for new selections and preserves labels on existing groups and records. The teacher-owned management UI does not physically delete or reparent entries; existing shared-catalogue admin operations remain available.
- A category is either Year or Student category, with a free-form label. A name in at least one language is required; the other language is optional and falls back to the supplied name. Both may be supplied. Trim names and bound each to 120 characters. No fixed list of grades or student types limits custom values.
- Replace the combined group-offering dropdown with separate Subject and Year / student category selectors. Show platform choices and the current teacher's active custom choices. Add inline Add subject and Add year/category controls; a successful addition selects the new item without losing unsaved group details. Invalid input retains fields and shows a localized error.
- The existing details → weekly schedule → review/publish flow remains. Saving or resuming a draft retains its selected subject/category. Existing archived selections remain readable and may be retained unchanged; changing to a different selection requires active choices.
- Profile specializations use the same allowed choices. Editing a name updates its labels wherever used; explain this when an item has existing references. Archiving does not hide already published groups.

## Schema approach and alternatives

Extend the existing subjects, education_nodes and offerings with nullable owner_teacher_id and archived_at. NULL ownership means the existing shared catalogue; teacher IDs mean custom entries. This preserves groups.offering_id, foreign keys, lessons and existing public projection result shapes. An additive migration leaves existing IDs, labels and user data intact.

Custom nodes have explicit custom_year or student_category kinds and parent_id NULL. Existing shared grade/university/year hierarchy validation remains. Subjects and category records are reusable within their teacher's catalogue; an offering represents a subject/category pair. A teacher offering may reference shared or same-owner components. A shared offering may reference only shared components.

Replace the current global offering pair uniqueness with a shared pair uniqueness rule and an owned (teacher, node, subject) uniqueness rule. Generate UUID-backed slugs internally, so Arabic names and identical labels used by different teachers work without slug input. Ownership is immutable for all catalogue entries. Kind, parent and offering component links are immutable for teacher-owned entries; existing shared-catalogue admin operations remain available.

Ownership references must not use ON DELETE SET NULL, which would turn private entries into shared entries. Keep account deletion and dependent catalogue cleanup consistent with the existing operator workflow, and test it. Lock selected catalogue rows in a consistent order during save/archive validation so concurrent archiving cannot turn a validated new selection into an invalid one.

Separate custom tables would require changing every group join and public RPC contract. Allowing teachers to edit the shared catalogue would contradict the selected ownership model and existing admin permissions. The owner-scoped extension is recommended.

## Authorization and visibility

Active teachers may manage only their own custom entries, including before approval; publication still requires an active approved teacher. Teachers cannot alter shared entries or another teacher's entries, forge ownership, or change a custom row into a shared row. Admin moderation and management of the platform catalogue remain available.

Replace unconditional catalogue-read policies with explicit shared, owner/admin and group-reference visibility. Unreferenced custom entries and drafts are private. Published group references expose the required labels when the teacher is active and approved. Active accepted members, the active owner and active admins retain authorized historical labels when a group is archived; accepted-member history does not require the original teacher still to be approved or active. Public reads use narrow predicates without granting anonymous access to private profile, membership or scheduling helpers.

Reading public labels does not permit selecting them. Teacher setup/profile queries must return only shared-or-own choices even when other published entries are readable. Database checks must also guard raw group insert/update, teacher specializations, save_teacher_profile, pairing/draft saves and publication. Compare ownership with the target group/specialization teacher, including admin actions. General student profile catalogue selection remains shared-only for new or changed values; unchanged historical values remain readable.

Public teacher specializations must not leak unreferenced or draft-only custom entries. Expose custom labels there only when an eligible published group references the pairing. Public groups, detail and discovery retain their existing result columns; discovery filters include visible custom labels and continue to hide draft-only entries.

Public discovery filter choices use shared entries and custom labels actually used by eligible public groups, independently of broader owner/history read permissions. Profile saves retain unchanged archived specializations through delta updates rather than deleting/reinserting all references. Duplicating a group with an archived offering gives an actionable refusal until its catalogue selection is updated, rather than creating a new archived selection.

Make subject/category pairing and draft save one atomic operation, with idempotent owned pair creation, concurrent-save protection, existing shared-pair reuse where applicable, and draft identity/status checks. Failed group saves must not leave partial pairings or change another teacher's catalogue.

Update teacher catalogue management, setup/profile data and forms, shared-catalogue admin queries, public specialization visibility and discovery catalogue choices. Preserve historical group detail labels, duplicate-group ownership, profile privacy, schedule generation and atomic publication. ## Monthly teacher renewal and free launch

The user additionally wants teachers to renew their requests each month, preparing for a monthly subscription model. Launch remains free. No teacher is charged, no payment details are collected, and no fees announcement is sent by this implementation. Actual payment collection/provider integration is a later release; announcing fees must not silently activate billing or retroactively create debts.

Separate initial teacher approval from monthly access. Approval establishes eligibility to teach; a private monthly-access record tracks the current access period, renewal requests and administrator decisions. Expiry or a declined renewal must not silently set the existing approved boolean to false or mark an account suspended. Suspension and initial-review decline keep their existing independent restrictions. Grant a first free monthly period at teacher signup and backfill existing active teacher accounts into a fresh free period, including pending teachers, without retrospective requests, charges or notification floods. Pending/declined teachers can explicitly self-renew in free mode and keep preparing drafts while their monthly access is active. Publication and public discovery always require both initial approval and current monthly access; a free grant never approves a teacher. Monthly expiry gating therefore applies consistently to draft preparation as well as approved teaching.

Show a bilingual Monthly access card in the teacher dashboard: Free launch, current period, expiry date in Cairo time, renewal state, and a Renew for next month button. The admin panel gets current/expired monthly-access filters and bounded owner/admin-only renewal/grant history; no monthly approval queue is needed while free renewals are immediate. Keep renewal/payment information outside publicly readable teacher profiles. Teachers cannot forge access dates, decision status, fees or their own grants through raw REST or RPC writes.

The user confirmed two policies: renewal takes effect immediately while fees are disabled, and expired access pauses all teaching access until renewal is approved. In free mode the renewal transaction itself grants the next period immediately; no administrator decision is required and no payment is implied. Auto-grant is distinct from automatic renewal: the teacher must explicitly click Renew each month. Future paid access requires a separately authorized grant through the eventual approved payment/review process; announcing fees alone does not switch modes. Free mode is the only operational plan in this release.

Renewals cover one calendar month, rather than a hard-coded 30 days. Store UTC boundaries and display them in Africa/Cairo. Anchor periods to the original start day/time, clamp short months without drifting the anchor, and test Cairo daylight-saving transitions. Permit renewal during the final seven days of a current period or after expiry, with at most one next-period grant and no unlimited prepayment/extension clicks. Granting an early renewal extends from the existing expiry; granting after a lapse starts a fresh period at grant time and resets the monthly anchor without backdating access. Any future pending paid-review request alone must not extend access; free renewal requests are granted atomically in this release. Duplicate submissions/decisions cannot stack periods; serialize decisions and period extension, and enforce one pending request per teacher and one grant per approved renewal event.

Compute effective access with a half-open interval (starts_at <= database statement time < expires_at), not a browser clock, cached JWT or an expiry cron job. On expiry, block the teacher teaching workspace and its teaching reads and writes: catalogue, specializations, group drafts/publication/duplication, schedules, lesson generation/editing/copy/cancellation, enrollment decisions and material upload/download. Check both route/action entry points and database RPC/direct-table/Storage paths; hiding navigation is insufficient. Include roster RPCs, material downloads/deletes, lesson exclusions and all permissive FOR ALL policies, which can also authorize SELECT. Write an explicit action-by-role/status/access matrix before implementation, with independent admin and accepted-student branches. Retain sign-in, sign-out, account/profile settings, monthly status, renewal and support access. Profile settings must preserve unchanged specializations while expired and must not become a bypass for editing/selecting teaching catalogue entries. Students already accepted keep their authorized lesson/material/history access, and active admins retain oversight; expiry never deletes data. Public teacher/group discovery and new/retried enrollment requests are unavailable until access is restored, while existing students can still reach their classes. Preserve legacy public RPC result shapes and use a narrow safe availability projection for any group-detail renewal message. Do not broadly alter current_role, is_group_owner or is_group_member: introduce explicit actor-aware teaching-access predicates so renewal/account support, student membership reads and admin authorization remain intact. Students retain their own cancellation rights. Once renewed, existing groups and teaching access resume without republishing or recreating records.

Extend the private transactional email outbox with a teacher confirmation for a successful free monthly renewal, using existing canonical recipient/language rules and duplicate protection. Automatically granted free renewals do not create an admin approval queue or send review-request emails. Preserve an immutable renewal/grant history that can support separate request/decision events when paid review is designed later. Missing SMTP configuration does not prevent a valid free access grant or lose a request. Renewal dates and requests remain accurate without a scheduled worker; any scheduled reminders use only a supported deployment cadence and do not promise exact delivery times.

Prepare an admin-only bilingual announcement workflow for future fees: draft the message and proposed effective date, preview it with an audience count, then explicitly publish a persistent teacher-dashboard notice and enqueue individual emails to the selected teacher audience. Use an immutable announcement version and one event per recipient/version, with delivery status and retry support. Use canonical Auth email addresses without exposing the recipient list to teachers. Audience review must specify included account statuses and snapshot recipients at publication. Message delivery remains independent of monthly access and never activates charging. The current rollout publishes no fee announcement; the administrator uses this workflow when a fee policy is ready.

Add a separate reviewed monthly-renewal phase after initial approvals and outbox foundations. Test free defaults/backfill, calendar-month anchors and DST, early/late renewal, concurrent/repeated free grants, renewal-window limits, full expired-teacher workspace/RPC/raw REST/Storage restrictions, renewal/account exceptions, unchanged initial approval, public discovery/enrollment gates and preserved existing-student/admin access. Test announcement ownership, preview, recipient snapshots, deduplication, bilingual rendering and partial email failures. Report payment integration as deferred, not as implemented subscription billing.
