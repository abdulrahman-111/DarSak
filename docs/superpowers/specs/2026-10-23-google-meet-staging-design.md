# DarSak: staging teacher-owned Google Meet

Reviewed baseline: `/workspace/DarSak-meet-staging`, `origin/main` / `83046cd`, 2026-10-23. Design only; this reviewer changed no product code, schema, hosted environment, Google resources, or user data. This is a scoped design/security review, not a completed Codex Security scan. Parent reports separate free staging resources now exist: Supabase `dmbepdjwjmuelqcfzjae`, Vercel `darsak-staging` / `prj_wg0lJbQH38LGZGqATdLvshgJrGBq`, whose Git production branch is `staging`; Vercel production deployment status is therefore distinct from the application's staging environment.

## Decision

Use **Google Calendar events with a unique Meet conference per lesson**, owned by the teacher's connected Google account. Start with its primary calendar. Connecting is a separate Account → Integrations flow; existing Supabase Google sign-in is not consent for Calendar access. New future lessons created/generated after connection get automatic meetings; offer explicit “Prepare meetings for existing future lessons” later or as a bounded teacher action, never silent historical backfill. AI, recordings, transcription, attendance import, student invitations, cross-calendar sync, and paid services are outside this slice.

| Choice                                          | Fit and tradeoff                                                                                                                                                                                                                                                                                                                                                  |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Calendar event + `conferenceData.createRequest` | Fits scheduled lessons; supports start/end changes and cancellation, deterministic client event IDs for duplicate-safe retries, and teacher calendar visibility. Requires Calendar event permission and asynchronous conference completion. Recommended.                                                                                                          |
| Meet `spaces.create`                            | Narrow `meetings.space.created` scope and direct meeting URI, but no scheduled event, no delete-space method, and its create API exposes no client idempotency key. Network ambiguity can create duplicate orphan spaces. Google's Node quickstart lists a Workspace account with Meet enabled, so do not promise support for every free personal account. Defer. |

Google documents asynchronous conference generation and unique conferences per event, plus client-selected event IDs to prevent duplicate creation ([create events](https://developers.google.com/workspace/calendar/api/guides/create-events), [events resource](https://developers.google.com/workspace/calendar/api/v3/reference/events)). Meet's documented create contract and prerequisites support the comparison ([spaces.create](https://developers.google.com/workspace/meet/api/reference/rest/v2/spaces/create), [Meet quickstart](https://developers.google.com/workspace/meet/api/guides/quickstart/nodejs)).

Free accounts can host Meet, but personal accounts are limited to 100 participants and unsubscribed meetings with three or more participants to 60 minutes; one-to-one meetings can run up to 24 hours. Show a short connection-page notice; do not claim that creating a link upgrades these limits. Workspace administrators can also restrict capabilities. Validate a personal Gmail test teacher and a Workspace test teacher before claiming both supported ([Google Meet requirements](https://support.google.com/meet/answer/7317473?hl=en)).

Standard Calendar and Meet API usage is currently available at no additional cost; current official docs also announce potential charges for exceeding limits later in 2026. Keep this staging app unbilled, bound batch sizes/retries, and request no quota increases. Recheck pricing before a future production launch ([Calendar quotas/pricing](https://developers.google.com/workspace/calendar/api/guides/quota), [Meet quotas/pricing](https://developers.google.com/workspace/meet/api/guides/limits)).

## Repository constraints

- `src/features/platform/actions.ts`: `saveLesson` calls `create_lesson`; `generateLessons` calls `generate_lessons`. Status/copy/delete/group cancellation also enter via teacher action files. These are not the only possible callers: authenticated clients can invoke granted SQL RPCs directly.
- Latest lesson functions are redefined by `20261014131808_monthly_teacher_access_enforcement.sql`; read these latest definitions, not just foundation SQL. Generation preserves `(group_id, slot_id, local_date)` identity and Cairo DST checks; editing recurring schedules intentionally does not edit generated lessons.
- `student/data.ts:lessonDetail` explicitly checks accepted enrollment; teacher lesson page checks group teacher ownership. Existing live helpers require active profiles and teacher access. Preserve these contracts.
- `dars_private` is not an exposed API schema. Existing email outbox demonstrates private tables behind narrowly granted public wrappers. Use that boundary rather than exposing a token table or adding the private schema to PostgREST. For this pilot, use teacher-JWT owner-bound wrappers because no staging service-role key is available. Credentials remain ciphertext; no browser-accessible wrapper returns a plaintext token.
- Public discovery/preview/calendar projections must remain free of join links. Keep meeting details separate from `lessons` and avoid adding links to `select('*')` data, notes, lesson materials, public ICS exports, notifications, or serialized public JSON.

## Integration and secrets

1. New server-only OAuth start/callback endpoints under `/api/integrations/google/…`; Account → Integrations exists only for active teachers when the staging feature is enabled. Create/sync operations also require current teaching access, approval, own group, and non-archived group. Disconnect should remain available even when teaching access expires.
2. Start with `openid email` and `calendar.events.owned`, offline access, and explicit consent when obtaining/replacing a refresh token. This scope covers events on owned calendars; do not request full Calendar or Drive. If preflighting primary-calendar `conferenceProperties.allowedConferenceSolutionTypes`, add `calendar.calendars.readonly`; event permission alone cannot call `calendars.get`. Alternatively handle an unsupported Meet create response with manual fallback, avoiding the metadata scope ([Calendar scope list](https://developers.google.com/workspace/calendar/api/auth), [calendars.get authorization](https://developers.google.com/workspace/calendar/api/v3/reference/calendars/get)). Prefer the smaller scope set in v1.
3. Create random 256-bit `state` and PKCE S256 verifier/challenge. Store verifier/state/session binding in a short-lived encrypted HttpOnly/Secure/SameSite=Lax flow cookie, and persist only state hash plus user/session and expiry server-side. Callback requires the same authenticated user/session and matching cookie/state, then atomically consumes the flow before code exchange. Reject expiry, replay, cross-user, missing cookie, and malformed parameters; cancellation cleans up. No tokens or verifiers in URLs, browser storage, logs, or response data. Redirect only to the fixed locale integration page.
4. Use exact configured callback origin/URI and allowlisted staging host; never derive it from an arbitrary Host/forwarded-host header. After confidential code+PKCE exchange, call fixed Google OpenID userinfo endpoint with returned access token server-side and require verified email/nonempty subject; do not parse or trust ID token, so no nonce/JWKS dependency is required. Store Google subject and display email separately from DarSak identity. A teacher can connect another Google account intentionally. Account replacement must not silently transfer management of existing events: require disconnect first, preserve old event ownership/generation identity, and do not reuse old event IDs against a new account.
5. Private integration table: teacher UUID, immutable connection UUID/generation, Google subject/email, granted scopes, AES-256-GCM encrypted refresh token (key version, random nonce, ciphertext/tag; authenticated data binds teacher+connection), connection state, timestamps. Encryption key is server env only, independent of the database. Access tokens stay only in server memory. Preserve an existing refresh token if Google omits one for the same Google subject; first connection without one is unsuccessful/requires consent. Never retain a previous subject's token. Mark `invalid_grant` as reconnect-required and stop retries; preserve the original safe UI error code, never provider bodies.
6. No browser table grants on tokens/flows/jobs; RLS as defense in depth, private schema, explicit revokes including PUBLIC, fixed search paths and narrowly granted authenticated wrappers. Public SECURITY DEFINER wrappers must check live `auth.uid()`/profile/session and constrain every query by that teacher. Owner-facing status RPC excludes ciphertext. A separate owner-bound worker credential RPC may return **that owner's encrypted ciphertext** to the server running with their JWT; ciphertext is not a browser secret and must remain protected by AES-GCM and the server key. It returns neither plaintext nor another owner's data. No service-role key is required for the pilot. Google recommends unguessable state and revocation handling; Testing external OAuth refresh tokens normally expire after seven days ([OAuth best practices](https://developers.google.com/identity/protocols/oauth2/resources/best-practices), [offline tokens and expiration](https://developers.google.com/identity/protocols/oauth2/)).

## Lesson lifecycle and recovery

- Private meeting row is keyed by lesson UUID; stores owner teacher, immutable connection ID, provider event ID, generation, desired revision, applied revision, mode (`automatic`/`manual`), status, validated join URL, safe error code, and timestamps. Retain cancellation/deletion tombstones/jobs until external cleanup settles; do not lose event IDs by cascading away the only record before cancellation. Manual fallback accepts a bounded credential-free HTTPS URL; generated Google Meet URLs must match `https://meet.google.com/xxx-xxxx-xxx` exactly, with no query/fragment/credentials.
- SQL triggers enqueue/coalesce durable meeting jobs in the same transaction as lesson insert/update/delete and group cancellation/archive, including RPC, generated, copied, admin, and direct write paths. Do not perform HTTP in SQL. Never enqueue a completed/past lesson or duplicate generated identity. On connection, future new lessons opt into automatic mode; preexisting lessons stay unchanged until a deliberate preparation action.
- Bounded server worker uses the initiating teacher's JWT, claims only their own jobs with a lease token, refreshes credentials server-side, reloads current lesson and connection state, and synchronizes only that teacher's event. One active lease per lesson and a single desired-revision comparison prevent stale responses from publishing a cancelled or replaced link. If the revision changes during HTTP, requeue newest work and suppress stale publication. No general service-role worker or unattended runner is needed in the pilot.
- Derive a valid lowercase base32hex/hex event ID from deployment namespace + connection UUID + lesson UUID + event generation. Insert with that fixed ID, private visibility, no attendees, guest modifications/invites disabled, UTC RFC3339 start/end, minimal title, `conferenceDataVersion=1`, and one persisted conference request ID. On timeout/409 GET the same event and verify private DarSak identity markers before adopting it; do not blindly insert a random replacement. Conference status `pending` remains pending until bounded GET retries; only `success` with a valid video URI becomes joinable. A fresh request ID is required for a deliberate new conference attempt after failure.
- Reschedule patches the same event's current title/start/end with conference support; it does not create another meeting. Cancellation/delete/archive hides the join link immediately in the read projection, then deletes/cancels the Google event; treat 404/410/already-cancelled as success. Rescheduling a previously cancelled/deleted event requires a new persisted generation/event identity. Completed lessons retain history and trigger no fresh meetings.
- Retry 429, retryable quota 403s, 5xx and network failures with bounded exponential backoff/jitter and persisted `next_attempt_at`; respect Retry-After. Permission/unsupported conference errors become actionable fallback, token revocation becomes reconnect-required. Leases expire safely. Show Pending / Ready / Needs reconnect / Failed with teacher Retry and Paste manual link actions; Google failure must never roll back lesson creation.
- Manual override atomically switches mode/revision, hides old generated URL, and enqueues cleanup of an existing automatic event before discarding its identity. Pending workers cannot overwrite the manual link. Do not automatically retry while manual mode is active. Copying lessons never copies meeting links.
- Join read is a narrow authenticated RPC or authorized server projection: current active teacher-owner, or current active accepted student; scheduled lesson, non-archived group, current active/approved teacher as appropriate. Recheck membership on every read; no shared caching and no anonymous join endpoint. UI is on teacher/student lesson workspace, no open-redirect proxy. DarSak controls disclosure, not Google admission: a copied link may still work externally and teacher host controls determine admission.
- Disconnect stops new work, hides automation controls, best-effort revokes Google token and deletes encrypted local credentials even if revocation fails. Existing Calendar events remain in the teacher's account; clearly tell the teacher future reschedules/cancellations require manual Google management after disconnect. Do not promise external deletion or immediate invalidation of an already shared Meet code. Account deletion follows the same token cleanup/revocation boundary.
- Free recovery: best-effort `after()` kick after successful actions, durable persisted jobs, authenticated teacher Retry/Sync pending action, and opportunistic bounded worker drain on teacher page load, all with that teacher's JWT held only for the request. Do not create unauthenticated mutating GET drains or retain JWTs as job credentials. Durable jobs survive restarts; progress requires a teacher visit/action while no unattended runner is configured. A later scheduled worker needs separately configured server credentials and authorization.
- Resource bounds: one flow row per teacher (new start invalidates old; 10-minute TTL), one coalesced job per lesson, maximum five automatic attempts, one claimed job at a time, at most three jobs / 20 seconds per drain, strict HTTP timeouts, and server-enforced drain rate limit per teacher. Existing 90-day generation limit remains. For initial pilot, prepare at most 100 future meetings per teacher at once; excess lessons remain visibly “Not prepared” and eligible for a later bounded preparation action, never silently claim Ready or block lesson creation. Counters/lease/retry bounds live in SQL so clients cannot bypass them. Reuse existing teaching quota foundations rather than relaxing them.

## Staging isolation (must precede enabling OAuth)

- Introduce explicit application environment (`local`, `staging`, `production`); neither `NODE_ENV=production` nor `VERCEL_ENV=production` proves this is the production application. The dedicated `darsak-staging` project serves its staging branch as a Vercel production deployment. Automatic Meet requires server flag + `APP_ENV=staging` + exact staging Supabase allowlist (allow local only with a separate explicit local flag). Production application routes/actions stay disabled even if a public UI flag is forged. Optionally bind to the known staging Vercel project ID when the deployment exposes it; do not require `VERCEL_ENV=preview`.
- Centralize Supabase destination validation and call it from browser/server/admin clients and worker/route setup before any network call. Nonproduction accepts only local loopback or allowlisted staging origin `https://dmbepdjwjmuelqcfzjae.supabase.co`; missing/invalid/mismatched values fail closed. Explicitly deny the known production ref in nonproduction. Do not use “not equal production” alone, and do not trust a user-supplied flag. Production requires explicit production app configuration plus actual production hosting context; a production-looking `.env.local` cannot authorize a preview. Record the real production ref without exposing any keys. Public/browser configuration needs an equivalent non-secret environment label so guard decisions do not diverge.
- Separate free Supabase test project, synthetic fixture accounts/data, separate OAuth client, server encryption key, and preview-only env values. No production database clone, service key, SMTP password, migration application, linking, Auth settings, or environment changes are part of this code/design work. Existing production mail worker must stay disabled in staging. Use a stable staging Vercel preview alias for OAuth's exact redirect URI; random preview URLs are not wildcard Google callbacks.

## Scoped implementation tasks and acceptance

1. **Safety/config first:** guarded shared Supabase configuration (including existing admin helper), staging Meet gate, env example and setup guide. Tests: Vercel preview + `NODE_ENV=production` + production Supabase URL rejects; only approved staging/local targets pass; disabled routes perform no network.
2. **Private schema/RPC artifact only:** integration/flow/meeting/job tables, teacher-JWT owner-bound wrappers (including encrypted credentials, never plaintext), authorized metadata/join/manage RPCs, transactional enqueue/coalesce triggers and delete tombstones. Generate migration using Supabase CLI; apply only to disposable local DB for verification. Test anonymous/other teacher/pending/rejected/removed/suspended students cannot read links/ciphertext or invoke privileged management; accepted students can read only current join data. Verify generation conflicts/DST/exclusions remain unchanged.
3. **Server provider/OAuth:** isolated Google HTTP adapter, encrypted storage, state/PKCE/userinfo flow, refresh/revocation and connection generation. Tests: replay, tampered/cross-session callback, fixed redirect, missing refresh token, Google subject replacement, wrong encryption AAD/key, error redaction. Real consent awaits Google console setup.
4. **Synchronizer:** deterministic event IDs, durable lease/revision worker, bounded retry classification, pending conference polling, reschedule/cancel/manual transition cleanup. Mock HTTP contracts for network timeout after successful creation, 409 reconciliation, pending→ready, 429, revoked token, concurrent retry, cancellation during HTTP, manual override during HTTP, delete tombstone and reconnect-account boundary.
5. **EN/AR UI and hooks:** teacher account integration card/page, lesson meeting controls and accepted-student Join card, post-mutation kicks plus explicit retry. Test both locales, expiry/failure/fallback copy, cancelled lesson hiding, no public/discovery/ICS link leak. Validate lint/typecheck/unit tests and production build; run focused SQL isolation tests locally.
6. **Independent Sol review:** inspect immutable patch and test evidence, trace auth→private storage→Google call→join disclosure and staging guard. Correctness/security review must not be called a Codex Security scan unless the actual scan workflow is separately run.
